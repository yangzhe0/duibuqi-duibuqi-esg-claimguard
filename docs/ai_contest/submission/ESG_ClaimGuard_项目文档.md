# 1 项目概况

## 1.1 背景和基础

ESG 报告的复核不是简单的全文搜索。以“温室气体排放总量”为例，复核人员至少要确认四件事：报告是否披露该指标；数值对应哪一年、哪个主体和哪个口径；单位是否与相邻表格一致；结论能否回到原文页码。实际报告往往长达数十至数百页，信息分散在段落、表格、脚注和附录中。人工逐页查找耗时，纯关键词又容易漏掉同义表达和表格字段。

直接让大模型回答整份 PDF 也没有解决责任问题。回答可以很流畅，但若没有稳定页码、逐字引文和数值来源，复核人员仍要从头翻阅原文。FinQA 等金融文档研究表明，长文档中的文本、表格和多步数值推理需要明确的证据与推理结构 [4]；ESGReveal 等工作也采用检索增强方式处理异构 ESG 报告 [5]。本项目在此基础上进一步把“回答问题”改造成“交付可复核证据”：模型只能在候选原文中抽取，程序再检查页码、区块、引文、数值和单位。

因此，ESG ClaimGuard 要解决的核心问题是：**如何在不牺牲原文可追溯性的前提下，从长篇 ESG 报告中识别指标披露，并把模型输出转化为可查看、可处置、可导出的复核任务。**

![系统端到端流水线](latex/figures/fig_pipeline.png)

图 1 是全文主线。公开报告先形成可校验的数据清单，经版面解析得到带页码和坐标的区块；ESG-65 指标池从中召回候选；大模型返回固定字段；证据门决定一条结果能否进入正式数据；最后由工作台展示原文、结构化结果和问题处置入口。

项目已经完成 200 份报告的正式运行，共 10,528 页、65 项指标和 13,000 个“报告×指标”任务。最终得到 found 7,688 条、missing 5,312 条、error 0。这里的 found 仅表示候选通过内部证据合同，missing 仅表示当前解析与召回范围内没有找到合格证据，二者都不是对企业披露质量的评价。

## 1.2 场景和价值

目标用户是企业报告编制人员、合规人员和内部审阅团队。一次典型预审从选择报告开始：系统列出需要关注的问题；复核人员查看冲突数值、计算式或缺失提示；点击证据后回到 PDF 原页；最后记录“确认问题、已修正、待补材料、接受风险或判定非问题”等动作，并导出工作底稿。

![披露预审与问题处置界面](docs/ai_contest/assets/product_preaudit.png)

图 2 是当前系统的实际页面。左侧是同一报告下的问题清单，中间给出问题事实、原文证据和可追溯路径，右侧记录处置。系统将原先散落在搜索、复制和表格登记中的步骤集中到同一界面，但不替代人员作最终判断。

| 方法 | 可以完成的工作 | 仍需解决的问题 |
|---|---|---|
| 关键词或正则 | 精确复现已知词语 | 同义表达、表格和上下文覆盖不足 |
| 整份 PDF 自由问答 | 快速概括内容 | 页码、逐字引文和缺失判断不稳定 |
| 普通切块 RAG | 返回相关片段并生成回答 | 通常不强制数值来源和证据合同 |
| ESG ClaimGuard | 按指标给出页码、区块、引文、数值来源与处置入口 | 仍受 OCR、指标口径和人工判断约束 |

项目价值不在于给出一个看似精确的 ESG 分数，而在于缩短证据定位路径：人员不必从报告第一页开始翻找，可以直接核对系统给出的候选页和原文，把时间用于口径判断和问题处置。

## 1.3 所需支持

正式版本采用单机顺序运行。MinerU 完成版面解析后释放相关资源，Qwen3.6 再执行抽取，两类模型不同时占用显存。本次正式运行使用 NVIDIA GeForce RTX 5090（32,607 MiB 显存）、AMD Ryzen Threadripper PRO 9955WX 和 124.8 GiB 内存。网页端采用 React/Vite，服务端采用 Python。

在其他环境复现完整链路，需要准备有权处理的报告、MinerU 环境、Qwen3.6 模型权重和相应 GPU；只审阅冻结结果、运行 API 和前端不需要重新执行模型。若用于正式监管报送或鉴证业务，还需由法律、审计和行业人员确认适用标准、指标口径和责任边界。

# 2 项目规划

## 2.1 整体目标

项目没有把目标写成笼统的“提升 ESG 智能化水平”，而是拆成六个可以验收的问题。

| 待解决问题 | 设计目标 | 仓库中的验收依据 |
|---|---|---|
| 报告来源难追溯 | 保存公告、PDF、文件哈希和下载状态 | `data/report_index.csv`、`download_log.csv` |
| 复杂 PDF 难以统一读取 | 保留页码、区块类型、文本和坐标 | 解析清单与规范区块数据 |
| 指标任务容易漏跑或重复 | 建立报告与 ESG-65 的完整任务网格 | 13,000 个唯一键，error 0 |
| 大模型输出无法核对 | found 必须绑定页码、区块和逐字引文 | `validation.json`、`evidence_hardening.json` |
| 数值处理不可解释 | 分开记录值、单位及其来源 | 正式 CSV/JSON 结果表 |
| 结果无法进入实际复核 | 展示原文、问题、处置和底稿导出 | Dashboard 页面、API smoke、测试 |

## 2.2 技术创新点

第一，建立“来源—文件—解析区块—抽取结果”的连续数据谱系。每份正式报告都有来源 URL、PDF SHA-256、解析文件 SHA-256；每条 found 又保存 report_id、page_no、block_id 和 evidence_quote。它使问题能够从结构化结果反向追到公开报告原文。

第二，将大模型限制在候选证据内。系统不是把整份报告一次塞入上下文，而是先按版面解析，再利用指标名称、别名和语义相关性召回候选区块。模型负责处理同义表达，程序负责控制输入范围和输出格式。

第三，设置独立于提示词的证据门。found 不由模型一句话决定：指定区块必须存在，页码必须一致，引文必须是该区块原文的连续子串；定量结果还必须保存数值和单位来源。不合格结果进入重试、纠错或保守降级，不直接进入正式 found。

第四，把抽取记录转换为复核流程。系统在声明、证据、可计算约束和适用条款之间建立关系，生成三级问题而不伪造连续风险分数。人员可以查看依据、记录处置并导出底稿，模型结果由此成为工作对象而不是演示文本。

# 3 实施方案

## 3.1 技术可行性分析

技术链条所需的每个环节都有可用基础：巨潮资讯提供公开披露报告及公告元数据；MinerU 可把 PDF 转换为保留版面信息的结构化内容 [2]；Qwen3.6 用于候选内容的结构化抽取 [3]；CSV、JSON、SQLite 和网页 API 能承载可复验结果与处置记录。项目实现的重点不是重新训练基础模型，而是把这些能力组合成受证据约束的完整流程。

风险主要来自数据而非算力。扫描件可能出现 OCR 错字，跨页表格可能丢失表头，报告可能使用不同单位或省略适用范围。系统采用页级区块、候选扩展、精确引文校验、数值来源字段和回原文界面应对；无法消除的不确定性保留为 missing 或问题提示，不自动升级为违规结论。

## 3.2 技术细节

### 3.2.1 数据获取、筛选与冻结

本项目的数据入口是巨潮资讯全文检索。下载脚本请求公开检索接口，关键词为“ESG报告”，按公告时间分页读取。每条公告先检查附件类型和标题，排除摘要、提示性公告、发布通知、英文重复件和明显非 ESG 报告，再从静态附件地址下载 PDF。文件写入临时 `.part` 后检查 `%PDF-` 文件头，成功后原子改名，并计算 SHA-256。

![巨潮资讯 ESG 报告检索页](docs/ai_contest/assets/cninfo_search.png)

图 3 是 2026 年 8 月 31 日重新截取的实际检索页。仓库中的 `download_cninfo_esg.py` 实现同一检索逻辑。`download_log.csv` 保存 518 条检索处置记录；`report_index.csv` 最终登记 210 份 PDF。正式运行没有直接使用目录中的全部文件，而由 `input_manifest.csv` 冻结其中 200 份，并保存顺序、路径、文件大小、页数和 SHA-256；其余 10 份不参与本文统计。

数据不是一个大而含混的文件夹，而是五层明确对象：

| 层级 | 主要格式 | 关键字段 | 作用 |
|---|---|---|---|
| 检索日志 | CSV | 公告 ID、公司、标题、状态、错误 | 说明条目为何下载或跳过 |
| 报告索引 | CSV + PDF | 来源 URL、附件 URL、本地路径、SHA-256 | 连接公开来源与原始文件 |
| 冻结队列 | CSV | order、report_id、pdf_sha256、expected_pages | 固定正式运行范围 |
| 规范解析 | JSON | page、type、bbox、text/table HTML | 保留页码、表格和版面坐标 |
| 抽取结果 | CSV/JSON | status、value、unit、quote、page_no、block_id、lineage | 支撑检索、验证和工作台 |

### 3.2.2 问题形式化

设冻结报告集合为 `R`，指标集合为 `I`，任务集合为 `T = R × I`。本次运行中 `|R| = 200`、`|I| = 65`，所以 `|T| = 13,000`。对任务 `t = (r, i)`，系统输出状态 `z` 和证据对象 `e = (page, block_id, quote)`；若结果包含定量值，还输出 `v`、`u` 及其来源 `origin`。

模型建立在三个假设上：报告可以转为带稳定页码的规范区块；支持一条结果的原文可在一个或少量相邻区块中找到；自动结果只是候选，最终业务判断由人员完成。当扫描损坏、证据跨越大量页面或指标依赖报告外事实时，系统应保守返回 missing 或交由人员核对。

### 3.2.3 版面解析与候选召回

MinerU 将每页内容转换为文本、标题、表格、图片说明等区块，并保存类型和坐标。例如深康佳 A 报告第 43 页的首个规范区块是一个表格，保留了“关键指标—单位—2023 年—2024 年—2025 年”的表头以及温室气体、能源、水和废弃物等行。相比只抽取纯文本，这一结构能避免数值脱离表头和单位。

召回阶段以指标名称、别名及语义相关性筛选区块，只负责缩小搜索空间，不直接判断 found。未召回候选表示当前解析与检索条件下证据不足，不等于企业没有披露。

### 3.2.4 受约束抽取与证据门

Qwen3.6 读取一个指标和其候选区块，返回固定 JSON，包括状态、引文、页码、区块、数值、单位和说明。程序随后执行确定性校验：

```text
evidence_valid = block_exists
                 AND page_matches_block
                 AND quote_is_exact_substring_of_block

final_found = model_returns_found
              AND evidence_valid
              AND required_fields_complete
```

证据门不判断披露在业务上是否充分，只验证模型声称引用的文本确实位于指定原文。直接读取、公式推导、原文单位、归一单位和推断单位分别记录；若值由明确表达式得到，结果同时保存推导方法、表达式和输入。

### 3.2.5 声明约束与问题生成

业务层将一条声明表示为 `(subject, metric, period, value, unit, scope, evidence)`。系统比较同一报告中的数值、单位和证据关系，形成三类提示：结构化值无法在证据中定位；总量与分项在单位归一后不一致；当前候选范围未找到披露或省略说明。由于主体、期间和 scope 尚未在所有记录中完整结构化，复杂跨声明规则只生成复核候选，不直接定责。

### 3.2.6 产品工作流与工程验证

![系统总览与正式数据规模](docs/ai_contest/assets/product_overview.png)

图 4 是系统总览实际页面，展示冻结正式数据中的 200 份报告、13,000 个任务、59.1% 证据命中和 0 个 error。证据工作台把报告库、PDF 原页、抽取结果、逐字证据和修正表单放在同一屏；预审页则把约束问题与处置记录连接起来。

工程验证覆盖任务唯一性、状态枚举、证据合同、定量来源、manifest 一致性、SHA-256、Python 测试、API smoke 和前端构建。运行中 209 条因证据字段不满足合同而进入异常处置表：193 条在现有候选区块中重新截取了可逐字追溯证据，16 条保守改为 missing。该过程是内部工程纠错，不是独立人工测试集，也不用于计算准确率。

## 4.2 典型案例

以深康佳 A 2025 年 ESG 报告为例，系统对“温室气体排放总量”返回 113,126.46 吨二氧化碳当量，定位到第 43 页表格区块 `p43:b0`。原文引文为“温室气体排放总量｜吨二氧化碳当量｜-｜117,319.54｜113,126.46”，value_origin 和 unit_origin 均为 direct。

![PDF 原文、结构化结果与逐字证据同屏](docs/ai_contest/assets/product_evidence.png)

图 7 不是示意图，而是工作台读取正式数据后的实际页面。中间显示原报告第 43 页，右侧显示结构化值、单位、页码、区块类型和逐字证据。复核人员可以对照 2024/2025 年列判断数值是否取对，并在下方记录修正。

系统也会展示不能直接通过的记录。例如永杉锂业报告中，“废弃物产生量”结构化值为 343,285.50 吨，但当前证据引文只出现分项 `48,816.28、199,458.66、343,235.59`，没有原样出现该结果。预审页因此生成“结构化数值无法在证据中定位”的阻断问题，而不是把模型值静默写入底稿。这个反例说明证据门和人工处置的必要性。

## 4.3 结果分析

![E/S/G 维度覆盖](latex/figures/fig_dimension_coverage.png)

## 4.4 模型评价与适用边界

本方案的可用性来自职责分离：MinerU 处理版面，召回模块缩小上下文，Qwen 处理同义表达，证据门验证原文存在，复核人员承担最终判断。出现问题时，可以沿来源 URL、PDF 哈希、解析哈希、页码、区块和结果 ID 定位原因；冻结 manifest 与校验和保证评审看到的文件与正式运行一致。

局限同样明确：OCR 错误可能让正确证据无法通过精确匹配；跨页表格和隐含单位仍需人工拼接；主体、期间和 scope 尚未在所有记录中完整结构化；当前没有独立人工测试集，因此本文不能回答语义准确率是多少，也不能宣称优于其他模型。系统适合报告发布前的证据定位和内部预审，不适合直接给出企业评分、违规结论、投资建议或法定鉴证意见。

## 4.5 结论

ESG ClaimGuard 回答了一个具体问题：怎样把长篇 ESG 报告中的候选披露，整理成复核人员能够直接核对的证据任务。项目从公开公告出发，保存来源与文件哈希；从 PDF 中保留页码、表格和坐标；用指标召回和大模型生成结构化候选；再以确定性证据门检查原文位置；最后在网页中展示问题、原文和处置记录。

在冻结的 200 份报告上，13,000 个任务全部得到最终状态，7,688 条 found 可以沿内部数据回到指定页码和区块，3,214 条定量结果保存了数值与单位来源。结合实际工作台页面，这些结果说明“公开报告输入—证据候选—问题处置—底稿导出”的工程流程已经跑通。

项目没有把工程完成偷换成模型准确，也没有把 missing 偷换成企业未披露。它的实际作用是先完成大规模、重复性的定位和整理，把证据是否充分、口径是否一致以及问题如何处置留给复核人员。这正是系统在报告发布前预审场景中的价值。
