# ESG ClaimGuard 题目分析与重构决策

> 状态：建模分析版（2026-08-09）  
> 结论：上一版“可信披露诊断台”产品评审不通过；保留数据与工程底座，停止继续扩写旧的加权排序方案。

## Model Contract

### 核心结论

本项目真正要解决的问题不是“把 65 项抽取结果排个顺序”，而是：**给定一份上市公司可持续发展报告，自动找出声明与原文证据之间的失配、报告内部的数值矛盾，以及应披露但没有说明的关键缺口，并生成可回溯、可复核、可导出的预审工作底稿。**

产品暂定名：**ESG ClaimGuard｜可持续披露一致性预审系统**。

这里的“预审”只核验公开报告内部的披露一致性和证据充分性，不判断企业实际 ESG 表现，不认定违法违规，也不替代鉴证或审计意见。

### 子问题与模型映射

| 子问题 | 首选模型 | 不可替代的证据角色 | 备选方案 | 失败切换条件 |
|---|---|---|---|---|
| 报告中有哪些可核验声明 | 约束式声明抽取 | 把段落、表格转为包含主体、指标、期间、数值、单位和口径的原子声明 | 规则模板抽取 | LLM JSON 合规率低于 98% 或单报告成本不可接受 |
| 哪些证据支持或反驳声明 | 声明—证据三分类推理 | 区分 supported / contradicted / insufficient，不把“召回到关键词”误作证据成立 | 规则蕴含判定 | 自然样本 Macro-F1 不优于单次 RAG 基线 |
| 多处披露是否彼此一致 | 约束图 + 数值一致性引擎 | 检查期间、主体、口径、单位、总分关系和比例关系 | 成对规则比对 | 图构建成本高但不提升错误检出率时退化为稀疏关系表 |
| 什么内容属于应核验缺口 | 交易所/GRI 条款映射 | 给出明确的标准依据和遗漏解释要求，而非用全语料 found 率冒充“同行标准” | 仅使用交易所规则 | 行业或标准版本无法可靠匹配时不展示该项 |
| 人工先处理什么 | 校准后的单位时间期望风险削减 | 把错误概率、影响等级和审核成本分开建模 | 严重等级字典序 | 人工标签或审核耗时不足时禁止输出伪精确 0—100 分 |

这五个模块分别回答“声明是什么、证据是否成立、声明之间是否一致、缺口依据是什么、有限时间先处理什么”，删除任一模块都会丢失独立能力，不构成模型堆砌。

## 一、对上一版的否决意见

### 1.1 模型名与算法实体不一致

上一版称“证据风险图”，实现却是对每条 `report-indicator` 记录计算四个手工分量后排序。代码中没有可查询的节点、关系、矛盾边或多证据推理，因此“图”只是产品文案，不是技术对象。

### 1.2 权重没有证据

`0.35R + 0.25U + 0.25G + 0.15F` 没有人工标签、专家赋权、敏感性分析或学习过程。即使展示四根贡献条，也只解释了公式如何计算，没有证明公式为什么正确。

### 1.3 评价存在自证循环

“自动规则风险”既参与优先级计算，又被当作 Risk Recall 的答案。高风险项排在前面是公式的直接结果，不能证明系统发现了真实错误。96.6% 的工作量削减同样是对这套内部规则标签排序后的派生量，不能作为人工审阅效率证据。

### 1.4 “同行缺口”不是同行

当前 200 份报告没有行业分类、上市板块、规模或适用披露规则的分组。全体语料 found 率最多是“语料出现率”，不能回答某家公司是否应该披露，更不能称为同行基线。

### 1.5 人工反馈不是学习闭环

当前保存反馈后，已复核任务退出队列，并用指标级 Beta 平滑改变其他报告的一个分量。这是状态更新，不是经过验证的主动学习或模型更新；而且“用于模型学习的样本价值”和“用于业务审核的风险优先级”被混在了同一队列中。

### 1.6 置信度不可校准

结果中大量 `llm_confidence=0` 是模型未稳定输出置信信息，不等于错误概率为 100%。直接对自报置信度做加权既没有概率语义，也没有校准验证。

### 1.7 用户完成不了一个完整工作任务

用户可以看结果、跳原文、打标签，但不能得到：矛盾的两处证据、适用的规则条款、建议处理动作、问题解决状态、可提交的预审底稿。因此当前系统更像研究数据浏览器，而不是报告编制或复核工具。

### 1.8 比赛证据不足

比赛明确要求严谨论证创新、与已有工作比较、展示 AI inference 指标并说明数据和行业知识来源。上一版只有系统内部统计，没有人工金标准、强基线、消融实验和用户效率实验，无法支撑“创新有效”。

## 二、重新定义用户和场景

### 2.1 唯一主用户

主用户是**上市公司可持续发展报告的编制复核人员或内部审阅人员**。研究人员和外部分析人员是次要用户，不再同时主导产品设计。

### 2.2 核心工作任务

> 在报告发布或提交前，用 10—20 分钟找到最可能影响披露可信度的内部矛盾、证据不足和条款缺口；逐项解决后，导出带页码、原文、处理记录和规则依据的预审工作底稿。

### 2.3 最小可用闭环

```text
上传报告
  → 抽取原子声明和全部候选证据
  → 构建声明—证据约束图
  → 运行数值、语义和条款三类核验
  → 展示“一项问题 + 两侧证据 + 规则依据”
  → 用户确认、修正、豁免或标记待补材料
  → 重新计算问题状态
  → 导出预审工作底稿
```

成功标准不是“页面有多少图”，而是用户能否在一份新报告上完成从发现问题到关闭问题的全过程。

## 三、声明—证据约束图

### 3.1 原子声明

每条声明定义为：

```text
c = (subject, metric, period, value, unit, scope, qualifier, evidence)
```

- `subject`：声明主体，例如集团、母公司、子公司、员工或供应商；
- `metric`：规范化指标；
- `period`：报告期、基准年或目标年；
- `value/unit`：数值及标准单位；
- `scope`：范围一/二、境内/境外、合并口径等；
- `qualifier`：目标值、实际值、累计值、同比值等；
- `evidence`：页码、block、bbox 和原文。

当前抽取结果只稳定保存了 `metric/value/unit/evidence`，下一版必须补齐主体、期间、范围和限定词，否则不同口径的数值会被错误比较。

### 3.2 图结构

令约束图为 `G=(V,E)`：

- 节点：声明 `C`、证据块 `B`、报告实体 `O`、期间 `T`、标准条款 `K`；
- 边：`supports`、`contradicts`、`same_metric`、`part_of`、`derived_from`、`governed_by`；
- 每条问题必须能回溯到至少一条声明和一段证据；矛盾问题必须同时展示冲突双方。

这时“图”才是可查询的数据对象，而不是排序算法的别名。

### 3.3 数值一致性约束

对单位归一化后的数值 `z_i` 和 `z_j`，同主体、同指标、同期间、同口径声明的相对差异为：

```text
d(i,j) = |z_i-z_j| / max(|z_i|, |z_j|, epsilon)
```

当 `d(i,j)>delta_m` 且不存在可解释的口径差异时，生成“同指标矛盾”候选。`delta_m` 按指标类型设定，并用人工样本做敏感性分析，不使用全局拍脑袋阈值。

对总分关系和比例关系分别检查：

```text
d_sum = |z_total - sum(z_part)| / max(|z_total|, epsilon)
d_ratio = |z_ratio - z_part/z_base|
```

所有单位换算、容差和推导过程写入问题卡，避免只有 LLM 结论。

### 3.4 声明—证据推理

对每个 `(claim, evidence_set)` 输出：

- `supported`：证据覆盖声明中的主体、指标、期间、数值和口径；
- `contradicted`：证据明确给出冲突信息；
- `insufficient`：证据相关但不足以支持或反驳。

不能仅把最终类别作为输出，还要返回最小证据集合。多段证据需要先分别判断，再在图上聚合，避免把无关长上下文一次性塞给模型。

### 3.5 标准条款核验

第一阶段只接入能够官方溯源的规则：

- 上交所《上市公司自律监管指引第14号——可持续发展报告（试行）》；
- 深交所对应可持续发展报告指引及现行编制指南；
- GRI Universal / Sector / Topic Standards 中项目实际使用的版本。

条款核验输出“已披露、说明不适用、未找到说明、需人工判断”，不把“未找到”直接写成违规。适用性需要结合交易所、板块、行业和公司属性。

## 四、优先级不再使用任意加权分

### 4.1 业务审核队列

当具备人工金标准后，对问题 `i` 使用单位时间期望风险削减：

```text
Priority(i) = p_i(issue) × severity_i / review_time_i
```

- `p_i(issue)`：在独立验证集上校准后的问题概率；
- `severity_i`：来自问题类型与适用条款的影响等级，不混入模型不确定性；
- `review_time_i`：该类型历史审核时间中位数。

在人工样本和耗时数据不足时，只展示“阻断/重要/提示”三级和触发依据，禁止伪装成精确的 0—100 分。

### 4.2 标注学习队列

用于提升模型的标注队列单独计算：

```text
Acquisition(i) = uncertainty(i) + lambda × diversity(i)
```

它服务于数据建设，不混入业务审核优先级。人工标注更新模型前必须经过离线验证和版本发布，不能每保存一次标签就无审计地改变生产判断。

## 五、评价方案

### 5.1 金标准数据

建立两个互补测试集：

1. **Natural-Gold**：从 200 份真实报告分层抽样声明，由两名标注者独立标注声明结构、证据集合和三分类结论；冲突通过第三人裁决，并报告一致性。
2. **ESG-Inject**：在不改变版式来源的前提下，对真实声明做可追踪故障注入，生成数值替换、单位交换、期间错位、主体/范围错位、总分关系破坏、证据删除六类错误。注入样本只验证已知错误类型，不能替代自然错误集。

建议最小规模：Natural-Gold 300 条声明、ESG-Inject 600—1000 条；每种错误和表格/段落证据都要覆盖。

### 5.2 端到端指标

| 能力 | 指标 | 说明 |
|---|---|---|
| 声明抽取 | 字段级 Precision / Recall / F1 | 主体、指标、期间、值、单位、范围分别报告 |
| 证据召回 | Evidence Recall@K、最小证据集合 F1 | 不能只算有没有 quote |
| 事实核验 | 三分类 Macro-F1、每类 Recall | supported / contradicted / insufficient |
| 数值核验 | 各故障类型 Precision / Recall | Natural-Gold 与 ESG-Inject 分开报告 |
| 置信校准 | ECE、Brier Score、risk-coverage curve | 验证“高置信”是否真的更可靠 |
| 系统效率 | 单页/单声明时延、显存/内存、失败率 | 对应比赛 inference 要求 |
| 用户价值 | 找出固定问题的耗时、漏检数、底稿完成时间 | 与人工 PDF 搜索、普通 RAG 对照 |

### 5.3 基线和消融

强制比较：

- Baseline A：关键词/正则；
- Baseline B：整份 PDF 单次大模型问答；
- Baseline C：普通 RAG + 单证据 LLM 判断；
- Ours：约束式声明抽取 + 多证据图推理 + 数值引擎 + 校准。

消融实验分别移除：图关系、表格结构、数值约束、标准映射、置信校准。只有新增模块对独立测试集或用户时间有可测提升，才保留为创新点。

## 六、产品界面重构

### 6.1 主流程只保留三屏

1. **报告预审**：上传/选择一份报告，显示处理进度和可关闭的问题，而不是全库 vanity metrics。
2. **问题工作台**：左侧问题队列；中间冲突双方或声明—证据对照；右侧规则依据、判断理由和处置动作。
3. **工作底稿**：按已解决、接受风险、待补材料和未处理导出，包含证据页码、处理人、时间和版本。

### 6.2 一张问题卡必须回答

- 哪一句声明有问题；
- 与哪一段证据或哪一句声明冲突；
- 系统依据了什么数值约束或标准条款；
- 为什么不是口径差异；
- 用户可以确认、修正、豁免还是补材料；
- 处理后问题是否真正关闭。

只展示单条抽取结果和四根信号条的旧卡片不能保留为核心交互。

## 七、现有资产处理决策

### 7.1 保留

- 200 份 PDF、来源台账和解析结果；
- MinerU 离线解析与任务状态持久化；
- Qwen3 结构化抽取调用框架；
- PDF 页码、block、bbox 证据定位；
- 上传、报告索引、复核记录与错误恢复基础；
- React 组件、PDF viewer 和整体视觉语言。

### 7.2 重构

- ESG-65 从“最终结果表”改为声明模板和条款映射入口；
- 抽取结果补齐主体、期间、范围、限定词和全部候选证据；
- `AuditPage` 改为双证据问题工作台；
- review 数据改为 issue-level，并记录动作、依据、版本和关闭状态；
- 评价脚本改用独立金标准与故障注入集；
- 健康检查扩展为任务恢复、模型版本和标准版本检查。

### 7.3 删除或降级

- 删除当前四项固定权重与伪精确优先级；
- 删除用自动规则标签评价同一规则排序的指标；
- “同行缺口”在没有行业元数据前不进入主产品；
- “人工反馈学习”在没有独立离线验证前只作为标注数据保存；
- 全库概览和质量页降为研发监控，不作为比赛主故事。

## 八、实施里程碑与工作量

| 阶段 | 目标 | 主要交付 | 预计工作量 |
|---|---|---|---:|
| M0 | 冻结旧方案 | 本分析、术语表、旧功能保留/删除清单 | 已完成 |
| M1 | 做出一个真实问题闭环 | 声明 schema、图存储、3 类数值约束、双证据工作台 | 1.5—2 天 |
| M2 | 建立可评价数据 | 注入工具、300 条 Natural-Gold 标注界面和协议 | 1—2 天开发，标注另计 |
| M3 | 加入 AI 核验 | 三分类 prompt、最小证据集合、校准、基线/消融 | 2—3 天 |
| M4 | 产品化交付 | 条款映射、工作底稿导出、任务恢复、演示样例 | 1.5—2 天 |

纯开发约 6—9 个高强度工作日；高质量人工标注不能由代码工时替代。一天内可以做出 M1 演示，但不能诚实地称为“比赛完成版”。

## 九、风险与失败预案

- **自然错误太少**：保留 ESG-Inject 用于覆盖已知故障，但论文中与自然集严格分开。
- **表格结构丢失**：优先使用 MinerU 单元格/行列信息；无法恢复时将问题标为证据不足，不强行比较。
- **标准适用性不明确**：隐藏自动结论，只展示候选条款并要求人工确认。
- **LLM 三分类不稳定**：退回规则核验和证据召回，LLM 只生成解释，不参与最终标签。
- **图方案无增益**：通过消融检验；若不提升多证据问题则退化为关系表，不保留“图创新”叙事。
- **没有审核耗时数据**：使用严重等级排序，不输出单位时间收益。

## 十一、设计评审结论

当前决策为：**有条件通过新方向，不通过旧实现继续扩展。**

进入代码阶段前必须满足：

- 用至少一份真实报告展示“同一声明的两处证据或一条可计算约束”；
- 明确 Natural-Gold 标注协议，避免再次用系统自身输出当答案；
- 旧权重模型不再作为产品核心或比赛效果证据；
- 一张低保真问题卡能够让用户完成发现、判断、处置和关闭。
